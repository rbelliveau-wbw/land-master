# PO Component Reallocation — Creator Handoff

The PO right panel proposes **one Budget Modification per selected cost code**.
Each modification can increase one element and offset it with reductions in the
other elements. The PO and every linked modification use the **same captured
approval round**. Zero or negative net changes still require that approval.
Standalone Budget Modification creation and its existing permissions are not
changed by this feature.

## New Native Field

Create this field in Creator **before saving the changed functions**:

| Form | Link Name | Native Type | Default | Purpose |
| --- | --- | --- | --- | --- |
| `Budget_Modification` | `Component_Reallocation` | Decision box / boolean checkbox | `false` | Explicitly identifies normalized signed component changes generated by this PO contract. |

This is a **new field**, not an existing catalog field. Do not add five direction
fields or replace the five existing currency fields. Keep the native
`Modification_Type` choices **Increase / Decrease**. Add the new flag to the
`All_Budget_Modifications` report's readable field layout and publish that report
with the field. Do not hand-edit historical generated schema files to imply that
a current native export was captured.

The existing `Labor_Budget`, `Materials_Budget`, `Equipment_Budget`,
`Subcontractor_Budget` and `Other_Budget` values are normalized by the record's
global direction: **actual signed delta = stored component × direction**, where
Increase is +1 and Decrease is −1. `Amount` is the absolute net change. A net-zero
record uses Increase with Amount 0. All five stored values must be present, their
sum must equal Amount, and the gross component movement must be positive.

Only records explicitly marked `Component_Reallocation=true` have this meaning.
Unmarked legacy components retain their existing nonnegative interpretation.
Existing aggregate rollups continue to use Modification_Type and Amount once;
they must not sum absolute component movements into the item total.

## Permissions And Report Visibility

Keep the established rights in
[`manifests/budget-request-permissions.json`](../manifests/budget-request-permissions.json).
No new User Access grant, profile, OAuth scope, API audience or approver role is
required or authorized by this feature.

| Audience | Required Behavior |
| --- | --- |
| Existing Budget/PO readers | Read the new flag wherever they can already read the five component amounts. Include it in the report field layout/field visibility; retain existing record ownership and View/View All restrictions. |
| Existing Budget editors / authorized PO creators | Compose adjustments only through the same authorized PO draft and selected cost codes. Native PO scope, actor, revision and phase-lock checks still apply. A create-only PO grant does not grant standalone modification or general Budget editing. |
| Existing in-flight PO editors | Retain the current Edit All restriction for amendments. No new submitted-record editing grant is introduced. |
| Assigned PO approvers | Review the signed changes in the existing PO bundle/email/workbook and approve through the assigned PO row. General Budget or Budget Modification edit rights are not needed for an ordinary assigned approval; retain existing profile exclusions. |
| Backend workflow functions | Set/read the boolean and signed component fields under the existing function execution context. Do not grant broad direct form editing to make a workflow succeed. |

Hide or make the marker read-only on ordinary native modification forms for the
existing non-admin audiences. It is a contract marker, not a user-selectable
permission bypass. Preserve existing component-field permissions; inspect native
field validations for a minimum-zero restriction before testing signed storage.

Profiles whose ordinary report exposes only their own modifications continue to
use the existing authenticated PO Get bundle fallback for another submitter's PO
children. That display-only fallback now carries the marker, direction and all
five normalized component values. Do not broaden report ownership access as a
workaround. A missing/malformed flag or incompatible bundle remains unavailable.

## Functions And Installation Order

The public endpoint remains `Manage_Purchase_Order` / its existing environment
binding; the key/value argument remains `payload`. The outer response remains
`po-v1`, with explicit `po-reallocation-v1` capability/captured-plan evidence for
the new behavior. No new Custom API registration is needed.

1. Create the boolean field and enable the matching **read** visibility for
   existing audiences; update the existing modification report field layout.
2. Save and compile the contract readers/validators:
   `poValidatePayload`, `poApprovalBundle`, `poSnapshot`, `poBudgetBalances`.
   The changed sources retain the current catalog's component-balance behavior;
   do not install an older extracted body over the current component contract.
3. Save and compile `managePurchaseOrder` and
   `handlePurchaseOrderApproval`, then the changed output helpers:
   `poExcelWorkbook`, `sendPurchaseOrderEmail`, `budgetElementExportRows`,
   `exportBudgetSnapshot`. Preserve their existing environment routing and
   notification sender/recipient behavior.
4. Verify the unchanged `recalcItemRevisedFinal`, `recalcBudgetModifiedTotals` and
   `poElementExportRows` together with the new readers. The existing approval
   handler changes the status of **every** captured linked modification in one
   PO chain. Its new final-decision preflight runs under the existing decision
   lock before recording a marked reallocation's final approval. Do not create
   or submit separate standalone approval chains.
5. Compile/save/reopen the changed native bodies in Development. Verify a
   read-only capability response before exposing committing controls. The user
   promotes the scoped Creator changes and report to Stage/Production; repository
   PMP does not publish Creator functions or add native fields.

## Financial And Recovery Checks

The backend must derive the required element increases from the actual PO lines,
fresh balances and the captured scope. User-edited increases cannot underfund the
PO or create unrelated budget increases. Reductions are limited to available
funds after other reserved POs, this PO's allocation and pending reductions.
Unknown legacy allocations cannot become spendable money.

An offsetting pair of unallocated historical modifications is still unknown even
when its net amount is zero. Use the explicit unknown-allocation count/completeness
evidence from the current balance contract, not just its signed net amount.

Preserve the immutable operation token, actor, revision, phase lock and captured
component plan. Lost replies permit targeted read-only Check/recovery; they do
not permit another blind submission. Pending reductions reserve funds for other
POs as well as pending increases providing their scoped credits. Rejection keeps
the established PO reservation lifecycle. Amendments exclude the previous own
reservation/adjustments exactly once and preserve the current captured approval
rules; deletion releases only the proven PO's allocations and recalculates
approved totals where required.

The current implementation keeps a submitted custom reallocation read-only.
Reject that PO before revising and resubmitting its adjustment; the new round
still approves the PO and every linked change together. Ordinary pending PO
amendments retain their existing behavior. A saved rejected-PO draft must reopen
its newly reviewed revision plan, rather than replacing it with the older rejected
bundle's plan.

Before the final approval of a marked bundle, re-read the selected items and
changed elements while holding the existing PO decision lock. Aggregate and
element funding can use the contract's supported pending credits. Donor
reductions additionally require actual available funds after all gross pending
reductions; positive pending credits cannot fund a donor reduction. A known
failure records no approval/financial change and releases that decision lock.
Nonfinal decisions, ordinary historical bundles and assigned notification retries
retain their existing behavior. This guard coordinates PO operations; it does
not make unrelated native form edits into a cross-form atomic transaction.

Approval emails and Excel attachments must show the actual signed component
changes, including a positive element-four amount alongside reductions in the
other elements. Net-zero records must remain visible in Requests, approved
element detail and Hide Empty. Aggregate totals stay unchanged when net is zero.

## Verification Limits And Native Gate

Local tests execute the actual checked-in reader/output bodies and native-shaped
fixtures. They are not proof of Creator compilation, signed currency storage,
profile field visibility or successful native publication. In particular,
negative values in existing USD fields and a marked Amount 0 require a native
Development test after the new boolean field exists.

Verify positive/zero/negative net changes; matching item/element identities;
committed-fund protection; repeated PO lines; stale/foreign/malformed plans;
pending reduction reservations; ordinary unmarked legacy records; assigned
approver access; a create-only profile's own draft; owner-scoped editing; the
single final approval; rejection; in-flight amendment; deletion; and lost-reply
read-only recovery. Confirm the email/workbook contains the five actual signed
deltas and that no separate modification email/approval chain was created.

Focused local checks include `test-budget-elements.mjs`,
`test-budget-hide-empty.mjs`, `test-po-requests.mjs`,
`test-budget-element-exports.mjs`, `test-budget-full-export-backend.mjs` and
`test-po-reallocation-readers.mjs`, `test-po-reallocation-final-approval.mjs`,
in addition to the domain/controller/native
submission regressions and the repository validation/Pages build.

## Rollback

Before any marked records exist, repository rollback may restore Budget Manager
122.29.109 through the environment mapping. Once signed records exist, use a
forward fix retaining BOTH signed-aware frontend and native readers. Do not
blindly map back to 122.29.109: its older element readers cannot interpret these
records correctly. Retain the new boolean and compatible bundle/balance
functions. Never clear the marker, rewrite signed amounts or delete linked
records as a deployment rollback.
